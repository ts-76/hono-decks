# Get started

Compile an MDX deck, mount the generated router in an existing Hono application, and verify it in your browser.

Upgrading from 1.x? Follow the [2.0 migration guide](https://github.com/ts-76/hono-decks/blob/main/MIGRATION.md) for configuration changes, renamed APIs, and removed features.

<section id={"prerequisites"}>

## Start with a working app

You need npm, pnpm, Yarn, or Bun and a running Hono, HonoX, or Void app. Framework-specific setup normally serves its sample at `/decks/welcome`; the generic CLI/file workflow uses `/decks/welcome`.

<Callout title={"Compilation and delivery are separate"}>

Compile MDX in your local development or build environment. The Hono app imports generated modules, so the deployed Worker does not need filesystem access.

</Callout>

</section>

<section id={"framework-init"}>

## Choose the setup for your application

For an existing Hono + Vite or HonoX application, install `hono-decks` and choose its integration. For Void, use the Void command; `--install` installs missing compatible Markdown dependencies using the app's package manager. Review the CLI output if it reports an unsupported configuration or an existing integration.

```sh
npm install hono-decks
# Choose one:
npx hono-decks init --framework hono
npx hono-decks init --framework honox
npx hono-decks init --framework void --install
npm run dev
```

Each integration preserves existing scripts and uses `virtual:hono-decks`; `dev` and `build` compile decks in memory. Open the sample URL printed by init, normally `/decks/welcome`. Hono and HonoX start with MDX; Void creates a Markdown sample with an interactive island. For supported versions, optional peer dependencies, and setup limitations, see the [package README](https://github.com/ts-76/hono-decks#readme).

For a Void setup using MDX, see the [Void example](/docs/examples?lang=en#void). This example does not require a Hono Markdown adapter.

Framework-specific setup ends here. The steps below describe the separate **generic CLI/file workflow**, useful for manual integration and Wrangler. Its `init` defaults to `/decks` and `compile` writes generated files to disk.

</section>

<section id={"install"}>

## Install the package and create the config

The example uses npm. `init` creates the build-only `decks/config.ts`, the app-owned `decks/index.ts` for runtime options, and a sample deck, and adds `.hono-decks/` to `.gitignore`. It refuses to overwrite existing files.

<CodeBlock filename={"Terminal"} language={"bash"} code={"npm install hono-decks\nnpx hono-decks init"} copyLabel={"Copy code"} copiedLabel={"Copied"} errorLabel={"Copy failed"} />

| Package manager | Install | Run the CLI |
| --- | --- | --- |
| npm | `npm install hono-decks` | `npx hono-decks <command>` |
| pnpm | `pnpm add hono-decks` | `pnpm exec hono-decks <command>` |
| Yarn | `yarn add hono-decks` | `yarn hono-decks <command>` |
| Bun | `bun add hono-decks` | `bunx hono-decks <command>` |

Replace `<command>` with `init` or `compile`, and use the same package manager for the remaining examples.

</section>

<section id={"deck"}>

## Create and compile the first deck

Create `decks/welcome/deck.mdx`. The first frontmatter block describes the whole deck; the next `---` starts slide one.

<CodeBlock filename={"decks/welcome/deck.mdx"} language={"mdx"} code={"---\ntitle: Welcome\ndescription: My first hono-decks presentation\n---\n\n---\nlayout: cover\n---\n\n# Welcome\n\nThis deck is served from my Hono app.\n\n---\n\n## Next slide\n\n- Write slides in MDX\n- Serve them with Hono"} copyLabel={"Copy code"} copiedLabel={"Copied"} errorLabel={"Copy failed"} />

Compile the MDX into Hono JSX modules. A successful run creates `.hono-decks/`.

<CodeBlock filename={"Terminal"} language={"bash"} code={"npx hono-decks compile"} copyLabel={"Copy code"} copiedLabel={"Copied"} errorLabel={"Copy failed"} />

**Generated files**

<FileTree label={"Source files"}>
  <File name={"decks/config.ts"} />
  <Folder name={"decks"}>
    <File name={"index.ts"} />
    <Folder name={"welcome"}><File name={"deck.mdx"} /></Folder>
  </Folder>
</FileTree>

`decks/config.ts` holds build settings that only the CLI reads. Edit the app-owned `decks/index.ts` and `deck.mdx` as needed. Never edit or commit `.hono-decks/`; each compile replaces it.

</section>

<section id={"mount"}>

## Mount the generated router in Hono

Add the generated router to the existing Hono app.

<CodeBlock filename={"TypeScript"} language={"typescript"} code={"// src/index.ts\nimport { Hono } from \"hono\"\nimport { decks } from \"../decks\"\n\nconst app = new Hono()\napp.route(decks.mountPath, decks.router())\n\nexport default app"} copyLabel={"Copy code"} copiedLabel={"Copied"} errorLabel={"Copy failed"} />

`decks.mountPath` is compiled from the config, keeping compile-time assets and runtime routes on the same public path. Mounting the router elsewhere fails with an explicit error.

</section>

<section id={"scripts"}>

## Use your existing development command

CLI init registers the package-private `#decks` import and prefixes existing dev/build/typecheck/test/deploy scripts with compilation. Do not edit or commit the internal `.hono-decks/` cache.

For cf projects, keep the custom compilation hook in `wrangler.config.ts` so deck edits rebuild during `cf dev`. See the Minimal example. For an existing Wrangler project, follow [Cloudflare’s migration guide](https://developers.cloudflare.com/cf/wrangler/migrate/) before using cf. Vite apps use `virtual:hono-decks` and do not write this cache.

<CodeBlock filename={"package.json"} language={"jsonc"} code={"{\n  \"imports\": {\n    \"#decks\": \"./.hono-decks/decks.ts\"\n  },\n  \"scripts\": {\n    \"dev\": \"hono-decks compile && cf dev\",\n    \"build\": \"hono-decks compile && cf build\"\n  }\n}"} />

</section>

<section id={"verify"}>

## Verify the generic workflow in the browser

<CodeBlock filename={"Terminal"} language={"bash"} code={"npm run dev"} copyLabel={"Copy code"} copiedLabel={"Copied"} errorLabel={"Copy failed"} />

Open `/decks/welcome` on the local URL printed by the dev server. The setup works when the Welcome slide appears and the controls or arrow keys move to slide two.

<Callout title={"Expected URL"}>

`http://localhost:3000/decks/welcome`. If your dev server selects another port, use the printed URL.

</Callout>

</section>
